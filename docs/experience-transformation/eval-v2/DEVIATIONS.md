# Evaluation v2 — deviations from PROTOCOL.md

1. **Local servers lost their sockets mid-run (2026-11-13 ~10:00 UTC).** Both evaluation servers (old on 4400, new on 4500) stopped accepting connections at about the same moment: the new server exited on SIGTERM and the old one stayed alive with no listening socket. Nothing in the evaluation sent either signal; another session on the same machine was running its own Next.js servers at the time, and the cause could not be established. Both were restarted on their own databases with the same configuration. Every scenario whose run failed while a server was down is re-run afterwards with the same run index, and listed below; the failed attempts are not graded.
2. **The new build's first pass found a crash, so the new build was re-evaluated in full on the fix.** At commit `6a8263c`, 2 of 10 trips in pass 1 (family-wellness-march, mountain-hiking) never finished building: a long stargazing stop stretched the day's window past 24:00 and the itinerary failed validation (`build_failed … invalid_model_response`, `days[0].window.endMinute > 1440`). That is an application failure and is reported as one. It was fixed in `83ecc69` (a sky-timed stop never stretches a day past midnight). Passes 2 and 3 of that build had failed outright because its server was down (deviation 1). The whole new-build sample was therefore discarded and re-run, three fresh passes on `83ecc69`; the discarded rows are kept in `runs/new-crashed-6a8263c/` for the record and are not graded.
3. **Servers are supervised.** After further unexplained SIGTERMs, each evaluation server runs under a supervisor that restarts it within seconds (`supervise-<port>.log` records every restart). Any scenario whose run failed with a refused connection is re-run with the same run index and listed here.
4. **Old build fill-in.** The old build's pass 2 lost beach-island, mountain-hiking and multigenerational, and its pass 3 lost all ten, to deviation 1; those were re-run with the same run indices on the same database.
5. **Geocoder refusals under parallel load.** While both builds scanned in parallel from one IP, the public geocoder answered `provider_failure` for whole proposals and five scans ended `discovery_failed … nothing_placed` (old: city-break, mountain-hiking and multigenerational in pass 3; new: tokyo-kyoto-transit and multigenerational in pass 1) — the app's honest response to a provider that did not answer, caused by the evaluation's own parallelism, and the same on both builds. From then on the builds ran one at a time, and each such scenario was re-run alone with its run index. One old pass-2 attempt (fill) failed on a page that never hydrated and was re-run the same way.
